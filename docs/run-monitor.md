## Import and access

Import `flows/vfc-run-monitor.json` into the same VFC workspace as Config and
the report flows. Generate a key on `Get report monitor` and a second key on
`Post backfill command`. The first protects the page, status and history; the
second protects the POST command.

The GET URL follows the lake API's VFC access-key convention:

```text
https://<vfc-host>/public/<tenant>/reports-monitor?key=<key>
```

Copy the actual host, tenant and GET key URL from its HTTP In node. The POST
key is entered separately in the page form; it is not stored in the page or
source code. Keep both keys out of source control. The page polls the status
route every 10 seconds and carries the GET key into its history request.

## Routes

| Request | Response |
|---|---|
| `GET /reports-monitor` | Self-contained page with status polling and a flow/month history form |
| `GET /reports-monitor?view=status` | JSON snapshot of SIH daily, shift, PBI build, PBI listener and Config status |
| `GET /reports-monitor?view=history&flow=<flow>&month=YYYY-MM` | Parsed rows from one monthly CSV log |
| `POST /reports-monitor/command` | Validates and queues one report backfill; returns 202, 400, 409 or 503 |

The GET routes are served by one access-key-protected endpoint,
`/reports-monitor`. The `view` query parameter selects the page (omitted),
status (`view=status`) or history (`view=history`), so the page and its read
requests share one VFC key. Unknown view values return 404. The history flow
must be one of `sih-hull`, `rpt-hull`, `pbi-report` or
`run-monitor`; months must be valid `YYYY-MM` values. Invalid
queries return 400, missing Config returns 503, absent monthly files return
404, and invalid data-lake responses return 502.

The history request lists only the selected flow's log folder, checks for the
exact `log_YYYY-MM.csv`, then reads and parses that single file. Checking the
listing first avoids the known data-lake behavior where reading a missing
object can wait without sending a message. The CSV parser honors quoted
commas and doubled quotes.

## Checkpoints in the report tabs
Six `Note status` nodes per report tab (SIH report daily, shift report) plus `Update run status` in the log lane:
| Node | Writes |
|---|---|
| `Note status: day list built` | every day of the run `queued` |
| `Note status: DAY SETUP` | the day `running` |
| `Note status: KPI hourly parts` | hourly parts n of m (413 fallback of the day KPIs) |
| `Note status: VALUE hourly parts` | hourly parts n of m (413 fallback of a product or order call) |
| `Note status: ASSET STOPS` | step `ASSET STOPS` (the call that fails on heavy days) |
| `Note status: JOIN & BUILD TABLES` | assets n of m at the day join |
| `Update run status` | the outcome from the log line: written, dry run, failed (with the text), nothing |

The first version had a checkpoint at the start of every lane (15 per tab) and put the SIH report daily tab at 204 nodes, over the VFC limit of 200 per workspace. The lane checkpoints between DAY SETUP and the stops (KPIs, KPI check, shifts, products, value KPIs, value check, assign, segments) were removed: a day that waits there shows step `DAY SETUP` and turns `STUCK` after 30 minutes. `validate-flow.js` now fails any tab over 200 nodes.

## Status snapshots

| Global key or source | Meaning |
|---|---|
| `runStatus_sih-hull` | Per-production-day state and the last SIH daily checkpoint |
| `runStatus_rpt-hull` | Per-production-day state and the last shift-report checkpoint |
| `runStatus_pbi-report` | Current job summary, last log line, and quiet/failure state |
| `runStatus_pbi-listener` | Pending events, queued jobs and the last released job |
| `runMonitorCommands` | The latest 50 compact accepted/rejected command records |
| `glob.get('cfg')` | Config readiness, platform and site count (credentials omitted) |

Status contains only small metadata. It never stores parquet rows or log-file
contents. The status route copies these values before decorating them. A
running status with no checkpoint for more than 30 minutes is returned as
`STUCK`; stored state is not changed by a monitor request. Per-day statuses
are retained by the report flows with a 100-day cap and age-based pruning.
The Config row is derived from the shared `cfg` value and exposes only its
platform and site count; credentials are never copied into the response.

The PBI listener's queue behavior is unchanged. Its monitor fields are
snapshots only. The PBI build's quiet state means that no new log line arrived
for the existing quiet window; it does not certify that every table was
written successfully. A failure state is preserved.

## Backfill commands

The page's POST command endpoint has its own VFC access key. Enter that key (a visible text field; the key alone or the whole command URL)
in the form; it is not stored in the page or source code. A command accepts
one flow and one range:

```json
{"flow":"sih-hull","start":"2026-09-01","end":"2026-09-30","force":false}
```

For the PBI report build, use `from` and `to` months instead:

```json
{"flow":"pbi-report","from":"2026-09","to":"2026-10","force":false}
```

SIH daily and shift backfills are inclusive and capped at 31 days. PBI
backfills are inclusive and capped at 12 months. Dates and months must be
valid; PBI tables and sites, when provided, must match the current Config.
An active flow or a queued PBI listener job returns 409 unless `force` is
true. Force does not cancel a current run; it permits a concurrent backfill.
Commands are retained as the latest 50 compact status entries and appended
to `<root>/logs/run-monitor/log_YYYY-MM.csv`.

The monitor flow includes these deliberately unconnected link-outs:
`to sih-hull BACKFILL`, `to rpt-hull BACKFILL`, and
`to pbi-report BACKFILL`. Each report tab has the matching `BACKFILL` link-in
feeding its existing settings node. After importing all four tabs, connect
each link-out to its matching link-in in the VFC. The command endpoint is
only operational after those three connections are made. Existing `DRY_RUN`
values are unchanged.
