# Run monitor: report status and monthly log history

| At a glance | |
|---|---|
| **What** | Read-only monitor for the SIH daily report, shift report and PBI report flows |
| **Flow** | `flows/vfc-run-monitor.json`, generated by `scripts/build-vfc-monitor-flow.js` |
| **Status** | Iterations 1a and 1b built and mock-tested offline. Import and runtime checks in the VFC remain |
| **Access** | One `http in` route with access `key`; generate its key in the VFC after import |
| **Status URL** | `GET /reports-monitor` serves the page; `/reports-monitor/status` returns JSON |
| **History URL** | `GET /reports-monitor/history?flow=sih-hull&month=2026-10` returns one month's log |
| **Writes** | None. The monitor only reads global status and the existing CSV logs |
| **History limit** | The newest 200 rows are returned; `count` and `truncated` report the total and omitted rows |
| **Tests** | `node scripts/test-vfc-monitor.js platform=legacy|xcelerator`; `node scripts/validate-flow.js` |

## Import and access

Import `flows/vfc-run-monitor.json` into the same VFC workspace as Config and
the report flows. Generate an access key on its `Get report monitor` HTTP In
node. The one key protects the page, status and history routes.

The URL follows the lake API's VFC access-key convention:

```text
https://<vfc-host>/public/<tenant>/reports-monitor?key=<key>
```

Copy the actual host, tenant and key URL from the imported HTTP In node. Keep
the key out of source control and do not paste it into a report or log. The
page polls the status route every 10 seconds and carries the same key into its
history request.

## Routes

| Request | Response |
|---|---|
| `GET /reports-monitor` | Self-contained page with status polling and a flow/month history form |
| `GET /reports-monitor/status` | JSON snapshot of SIH daily, shift, PBI build, PBI listener and Config status |
| `GET /reports-monitor/history?flow=<flow>&month=YYYY-MM` | Parsed rows from one monthly CSV log |

The routes are served by one access-key-protected endpoint,
`/reports-monitor/:view?`, so the page and its read requests share one VFC
key. Unknown subpaths return 404. The history flow must be one of `sih-hull`,
`rpt-hull` or `pbi-report`; months must be valid `YYYY-MM` values. Invalid
queries return 400, missing Config returns 503, absent monthly files return
404, and invalid data-lake responses return 502.

The history request lists only the selected flow's log folder, checks for the
exact `log_YYYY-MM.csv`, then reads and parses that single file. Checking the
listing first avoids the known data-lake behavior where reading a missing
object can wait without sending a message. The CSV parser honors quoted
commas and doubled quotes.

## Status snapshots

| Global key or source | Meaning |
|---|---|
| `runStatus_sih-hull` | Per-production-day state and the last SIH daily checkpoint |
| `runStatus_rpt-hull` | Per-production-day state and the last shift-report checkpoint |
| `runStatus_pbi-report` | Current job summary, last log line, and quiet/failure state |
| `runStatus_pbi-listener` | Pending events, queued jobs and the last released job |
| `glob.get('cfg')` | Config readiness, platform and site count (credentials omitted) |

Status contains only small metadata. It never stores parquet rows or log-file
contents. The status route copies these values before decorating them. A
running status with no checkpoint for more than 30 minutes is returned as
`STUCK`; stored state is not changed by a monitor request. Per-day statuses
are retained by the report flows with a 100-day cap and age-based pruning.
The Config row is derived from the shared `cfg` value and exposes only its
platform and site count; credentials are never copied into the response.

The PBI listener's queue behavior is unchanged. Its monitor fields are
snapshots only. The PBI build's quiet state means that no new log line arrived
for the existing quiet window; it does not certify that every table was
written successfully. A failure state is preserved.

## Offline checks and VFC verification

Run:

```text
node scripts/build-vfc-monitor-flow.js
node scripts/validate-flow.js
node scripts/test-vfc-monitor.js platform=legacy
node scripts/test-vfc-monitor.js platform=xcelerator
```

The mock test covers status transitions, stale-run detection, request
validation, missing history, CSV quoting and row limits. It also compares the
PBI report build's requests, output rows, paths, logs and errors with the
pre-monitor baseline. The VFC must still be checked for the optional
`view` route match, the access-key URL, and the `list objects` / `read object`
history request before relying on it.

## Backfill commands

The command endpoint and intentionally unconnected BACKFILL links are
iteration 2 and are not part of this read-only flow yet. Until then, use each
report flow's existing backfill inject.
