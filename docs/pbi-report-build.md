| At a glance | |

## Job (the inject payload)
`{"tables": [...], "sites": ["Hull", "Nottingham", "Weinheim"], "from": "2026-09", "to": "2026-10"}`. All optional: no list = all tables / all sites of `1.1 CONFIG` (since 2026-10-20 the sites and the root come from Config), no months = last month and this month (`from` and `to` are months YYYY-MM, both included; used by the month tables). **Only the tables in the job run** (a table that is not listed gets no message, whatever its `DRY_RUN`). `sites` limits the sites. An unknown table or site, or `from` after `to`, is refused before anything runs. Dry run per table: `DRY_RUN` in node `1.1 TASK SETTINGS`.

## Step 2: pbi_plan_opt and pbi_time_utilisation (2026-10-15)
- **Source:** `eu_report/pbi_report/source/plan_opt/site=<Site>/plan_opt_YYYY-MM.csv` (normalized layer). **Output:** `eu_report/report/<table>/site=<Site>/<table>_<YYYY-MM>_provideam.parquet`, one file per site and month; a rerun replaces the month. Columns are those of `scripts/lib-pbi-schemas.js` (`planSchema`, `utilSchema`); `source_hours` is empty (it only exists for the Insights Hub flow).
- **Per site (lanes 9 to 15):** list and read the site's Glidepaths file and build the target lookup in flow context (`targets_<site>`), read the Shift Patterns file into `shiftMap`, list the month files and keep the months of the job that exist (a missing month is logged: a read node would stop on a missing file), then one message per month, one per second: read the month file, build the rows, and write both tables. Per month a check line goes to the log (rows read, kept, left out, shifts without a mapping, machines without a target). A site whose Glidepaths or Shift Patterns file is missing is logged as FAILED and skipped.
- **Plan OPT rules** (from the report queries, `helper-pbit-outline.js --table "Plan OPT H"`, N, W, "Plan OPT Provideam", "Plan OPT EU"):
  - rows without a machine name are dropped. Hull: 19 machines and `GT4 - Auto` (list in node `Build plan rows`; the name `Bosch Capsulator ` has a trailing space). Nottingham: only AreaName ` Strepsils Packing` (leading space) and `SD Packing`, not `N11 Auto`, not `S14`. Weinheim: not `N11 Auto`.
  - Unique Machine Name = machine + `-` + site. Product Key = unique name + space + part name. Weinheim: the first 8 characters of the part name are cut off (the part code). Hull: text `Gavi 12 X 150 Russian Crypto` replaced by `Gavi 12 x 150 russian Crypto`. Trailing spaces of the part name are removed (the report data has none; leading spaces stay).
  - ShiftName = the `Shift` of the Shift Patterns file for the raw name (an unknown name gives an empty shift).
  - Total Time, Planned OpT, OEE Time: `H:MM:SS` to minutes `H*60+M`, seconds dropped (as the report: it splits on `:` and keeps two parts).
  - Targets: key = unique name + month start (`01/MM/YYYY`); OEE Target = bucket `% OEE`, PDT Target = `Planned Downtime (Total)`, UPDT Target = `Unplanned Downtime (Total)` of the Glidepaths file (an empty cell gives an empty target).
  - The report drops Defect Parts, Target, OEE, ShiftStartTime; the table has the other 17 columns.
- **Time Utilisation rules:** own machine rules (Hull: the same list; Nottingham: only 23 machines and not `N11 Auto`; Weinheim: all), computed from the raw rows (not from the filtered plan rows), minutes with seconds (`H*60+M+S/60`) summed per machine and day, All Time 1440.
- **Checked against the report** (`Plan OPT EU.parquet` of the report, Dec 2024 to 18 Sep 2026, Hull, Nottingham, Weinheim, run with `node scripts/test-vfc-pbi-report.js platform=xcelerator real plan dir=<dir>` and a pandas comparison): 99.80 % of the report's 39,928 rows are identical in all 17 columns (Hull 99.71 %, Nottingham 99.85 %, Weinheim 99.96 %). What is left is data, not rules: Sep 2026 rows changed after the report's snapshot (capacity, planned time of the last days) and 57 Hull rows of December 2025 that are in the report but not in our files (the gap days). 248 rows exist only on our side, almost all of Sep 2026 (the report stops on 18 Sep and the current month file is rewritten every hour). Time Utilisation has no sample in the report folder: checked against the plan sums (difference at most the seconds rounding, 0 machine-days without a plan row, no excluded machine present, 23 Nottingham machines).
- **Mistakes found by that comparison, fixed:** the glidepath files start with a byte order mark (`\uFEFFSite Name`, no target matched: the lookup removes it and the test fixture has one now); the Weinheim part code; the trailing spaces of the part name; `N11 Auto` in the Nottingham plan filter (an earlier filter step I had missed); and the normalizer was trimming all text (see sharepoint-files.md), which broke the Nottingham area filter and the Hull exclusion `Bosch Capsulator `.
- **Not tested in the VFC yet:** flow context (`flow.set` / `flow.get`) of the lookups between the nodes of a site, `list objects` on the month folders, one month message per second for about 70 months (3 sites x 23 months, roughly 2 minutes plus the writes), memory of a month of Nottingham rows (2,700 rows).

## Step 3: pbi_daily_losses (2026-10-15)
- **Source:** the line loss month file (`line_losses_YYYY-MM.csv`, one row per stop) plus four lookups: the volume loss correction month file (loss units and time), the plan OPT month file (volume total), the Equipment Coding file of the site and the Glidepaths file (loss targets). **Output:** `eu_report/report/pbi_daily_losses/site=<Site>/pbi_daily_losses_<YYYY-MM>_provideam.parquet`. A rerun replaces the month. Job: `tables` with `pbi_daily_losses` (it can be combined with the plan OPT tables: the site setup runs once per site).
- **Flow (lanes 11 to 18):** the site setup (Glidepaths, Shift Patterns) is shared with plan OPT and ends in `Route the site`; for losses the Equipment Coding file is read, the month files of the three types are listed and stored (`have_<type>_<site>` in flow context, so a missing optional file is never read), the months of the job that have a line loss file are chosen, then per month: correction lookup, volume totals, the line loss file, `Build loss rows`, decide, parquet, month path, write. A month without a correction or plan OPT file still builds (loss units or volume total empty).
- **Columns:** those of `lossSchema` of the Insights Hub flow plus four columns the report has: `comment` (the comment text), `merged` (machine + start time), `shift_name_copy` (the raw shift name) and `volume_day_key` (machine + day, the report's `Volume Key.1`). `volume_key` holds the report's `Volume Key` (date, machine, group, subgroup, description). `batch_id` and `comment_count` are empty. `target` = `value` / 100.
- **Rules** (report queries `Daily Line Losses H`, `N`, `W`, `Daily Losses Provideam`, `Daily Losses EU`, `Volume Loss Correction H/N/W`, `Equipment Coding H/N/W`, `Targets Volume`, `Targets Losses EU`), in the order of the queries, per site:
  - duplicate stops (same machine and start time) keep the first; rows without a machine are dropped. Hull and Nottingham: rows with an empty group or `0.Review Data` and the machines `B1 - Auto`, `B4 Auto`, `B5 Auto` are dropped.
  - Duration = `H:MM:SS` to whole minutes (seconds dropped). Breakdown Types = the raw subgroup (not Weinheim). Weinheim: the first 8 characters of the part name are cut. Product Key = unique machine name + space + part name.
  - the volume key is built from the date (dd/MM/yyyy), machine, group and subgroup (after the first replacements of the site: Breakdown - Mechanical/Electrical become Breakdown; Nottingham also Planned Losses and Unplanned Losses become Planned Loss and Unplanned Loss) and description, and joins the correction file, which gets the same replacements of its site. Loss Units = correction loss units (a whole number) x duration / correction time in minutes. No match: empty.
  - then the replacements after the join (Hull: Adjustments to Adjustment, Breaks and Meal to Meals & Breaks, Lack of resources to Lack of Resource; Nottingham: the last two), the Equipment Coding join (key machine + description; an empty equipment is `Unclassed`; a duplicate key doubles the row, as the report join does), the group filter (Hull and Nottingham: Not Logged, Planned Loss, Unplanned Loss; Weinheim has none), Text.Proper on the subgroup (Hull, Weinheim) and the final replacement list of the site (for example Meals & Breaks to Breaks / Meals, Minor Stop to Minor Stops, Other to Others, Adjustment to Adjustments). The replacements are text replacements of any part of the name, in the order of the queries.
  - loss target key = unique name + subgroup + month start (01/MM/YYYY); Value = the Glidepaths bucket with the same name for that machine and month; Target = Value / 100. Volume Total = the sum of the plan OPT Capacity of that machine and day (Hull without `GT4 - Auto`, Nottingham and Weinheim without `N11 Auto`).
  - the final machine lists: Hull the same 19 machines as plan OPT, Nottingham `Bosch`, `Fette 23`, `Fette12`, `Fette2`, `Fette20`, `Fette4`, `Fette5`, `Gran0`, `S14`, Weinheim none.
- **Checked:** the offline test (one check per rule, on synthetic files) and the real files of Aug and Sep 2026 (6 month files, 0 errors): loss units found for 99.8 to 100 % of the rows, shifts 100 %, volume total 100 %, equipment 84 to 99 %, targets 81 to 99 %, subgroup names inside the report set (Adjustments, Minor Stops, Breakdown, Quality Issues, Lack Of Resources, Reduced Speed, Others, Not Logged, Refilling Materials, Product Changeover, Start up and Sanitisation, plus the planned ones). **There is no sample of the Daily Losses EU table of the report, so it was not compared with it.** Hull on 15 Sep 2026 against our Insights Hub table: only GT4 is in both, and the Insights Hub table has 3 stops where the file has 25 (the Insights Hub downtime reasons are not the same data, an open point already in the diagram).
- **Open points:** the Power Query Text.Proper is replaced by a rule that capitalises each letter after a non-letter (same result for these names, not proven for others); joins with a duplicate correction key would double rows (none found, 0 duplicates in all files); the Weinheim `Run` rows stay in the table (its query has no group filter); Mira has no files.

## Step 4: the lake watcher (built 2026-10-16, not run in the VFC yet)
Own tab `PBI report listener` (`flows/vfc-pbi-listener.json`, 20 nodes, made by `node scripts/build-vfc-pbi-listener-flow.js`), because a VFC workspace holds 200 nodes at most and the report tab has 195. Test: `node scripts/test-vfc-pbi-listener.js` (35 checks, function code with fake flow and global contexts).
- **Events:** two `subscribe object` nodes, `/eu_report/pbi_report/source/` and `/eu_report/reference/` (subfolders included). Kept: `MODIFY` of a `.csv` of a known type (source: `plan_opt`, `line_losses`, `volume_loss_correction`; reference: `machine_names`, `shift_naming`, `glidepaths`, `equipment_coding`). Dropped: deletes, folders, other files, `format_list` (no table uses it). Nodes `Read source event`, `Read reference event`.
- **Collect:** node `Collect events` keeps one entry per source site+month or reference type+site in flow context `pending` (several events of the same file count once; the window starts at the first event). `LISTENERS_ON = false` in this node drops every event: use it during a bulk upload (the 204 month files would otherwise raise a few hundred events).
- **Release:** a clock (inject, every 30 s) runs node `Release due events`. Settings at the top: `SOURCE_WAIT_S = 120`, `REFERENCE_WAIT_S = 300` (both from the first event), `REFERENCE_MONTHS_BACK = 3`. An entry whose window is over becomes a job in the same format as the inject: source `plan_opt` -> plan OPT, time utilisation, daily losses of that site and month; `line_losses` or `volume_loss_correction` -> daily losses; months of one site and the same tables that follow each other are one job (`from`..`to`). Reference: `machine_names` -> `pbi_machine_names`; `shift_naming` -> shift naming plus the three month tables of all sites; `glidepaths` -> the three month tables of the site; `equipment_coding` -> daily losses of the site; the month tables run for the current month and `REFERENCE_MONTHS_BACK` months before it. The jobs are appended to the **global context** `jobQueue`; the debug node `Listener log` shows one line per job.
- **Entry to the builder:** the report tab has a clock `Job queue check every 10 s` and node `1.0 Take queued job`, which takes the oldest job from `jobQueue` and sends it to node 1.1 like the inject. One job per tick, so jobs run one after another. The manual run and the watcher are two triggers of one builder, and `DRY_RUN` of 1.1 applies to both. Tabs share only the global context, no wire between them.
- **No loop:** the report tables go to `eu_report/report/` or `eu_report/candidate/` and the log to `<root>/logs/`, both outside the watched folders (checked in the test).
- **JOB DONE:** node `25.2 Note last log line` in the report tab writes the time of every log line to the global context (`lastLog`, `done = false`). In the listener tab a clock every 10 s runs `Check quiet`, and the debug node `JOB DONE` shows one line when no log line came for 30 s. It means quiet, not all written.
- **Also in this build:** the loss months go 5 s apart (node `One month per 5 s`, was 1 s: with all months of three sites in one run the VFC stopped with `memory limit reached` in `15.3 Build correction lookup`).
- **Known limits:** `pending` lives in flow context and `jobQueue` in global context, so a restart of the VFC loses what is waiting (the next full job fixes that); the listener lines are in the debug node only, not in the CSV log (the jobs write their own log lines when they run); `pbi_calendar` is not rebuilt by the watcher (static, 2011 to 2050); the order of events is not guaranteed (delay 0.3 to 15 s), which the window absorbs.
- **Backfill (2026-10-16):** 2024-12 to 2026-10, all sites, all six tables, run by the user in the VFC in three jobs (2026-08..2026-10, 2025-01..2026-07, 2024-12). Checker on the 207 files: `problems: 0`, plan OPT 99.80 % identical to the report. A first run of 9 loss months at once failed once in Nottingham 2026-09 (memory), the 5 s rate fixed it. Aborting a long run by saving the flow works (queued months are dropped) but the log lane of the aborted run lost its lines until the next run.

## Step 5: the column names of the Tableau workbook (2026-10-17)
**Why.** Segun works in Tableau Desktop and uses the columns like for like; the workbook `EU Daily OEE Report - WIP5.twbx` is converted by a script to a workbook on the Insights Hub data source, so the files in the data lake must have the same column names (and types) as its four data sources. The first version of this build used the snake_case names of the Insights Hub flows (`site_name`, `good_parts`, ...): wrong for this purpose. Done in `scripts/lib-pbi-report-schemas.js`, the three row builders and the checker. The Insights Hub flows (`vfc-pbi-daily-hull.json`, `vfc-pbi-reference.json`) still use the old names: later, together with the reference files.

**What the workbook reads** (data sources of WIP5, read from the .twbx, and the converted parquet files in the lake at `Sandbox/report_test/`, which have the same names and types):
| Tableau source | Columns | In `pbi_report` |
|---|---|---|
| Machine Names EU | 6 | `pbi_machine_names`: the 6, then `loaded_at` |
| Plan OPT EU | 17 | `pbi_plan_opt`: the 17 in the same order, then `source_hours`, `loaded_at` |

`pbi_shift_naming` and `pbi_calendar` are not used by the workbook and keep their names. Our own extra columns stay (they are for the Insights Hub report) and follow the Tableau columns.

**Types** (the same as in the workbook's extracts): `Date` and `ShiftStartDate.1` are real `DATE` columns; `Good Parts`, `Total Time`, `Planned OpT`, `OEE Time`, `All Time` are integers; `Capacity`, `Downtime Units`, the targets, `Loss Units`, `Time in Mins`, `Volume Total` and the `... **Time of day.** In the workbook `Time` and `Duration` are Excel times on 1899-12-30. The parquet node cannot write dates before 1970, so they are written as timestamps on **1970-01-01** (same time of day, other date part). In the sheets of the workbook these two columns look unused (the sheets use `Time in Mins` and `Shift Time`); if a calculation uses the date part of `Time` or `Duration`, tell us. `Duration` and `Time in Mins` keep the seconds.

**What the parquet node can write (spikes 2026-10-16/17, tab `Date type spike`, results in `Sandbox/spike/`).**
| Engine | Type and value | Result |
|---|---|---|
| Legacy (`parquetjs`, the engine of all our tables) | `DATE` from a day number (days since 1970-01-01) | real `date32` |
| Legacy | `TIMESTAMP_MILLIS` from epoch ms | real timestamp; a negative ms (before 1970) is refused: `invalid value for TIMESTAMP_MILLIS` |
| Legacy | `TIME_MILLIS` from ms of a day | real time type |
| Legacy | text or a JS Date object in a `DATE` or `TIMESTAMP_MILLIS` column | read as a number and cut at the first non-digit (`2026-09-01` becomes 2026, 1975-07-20 as a date): send numbers only |
| Legacy | column names with spaces, dots and a dash; a null in every type; a row with missing keys | all work (checked in two tenants) |
| Modern (`hyparquet`) | `DATE` | `parquet unsupported type: DATE` |
| Modern | `TIMESTAMP_MILLIS`, `TIME_MILLIS` from numbers | written as a plain int64 / int32, no timestamp or time type |
| Modern | `TIMESTAMP_MILLIS` from a Date object or BigInt | error |
**Use the legacy engine.** Warning: the VFC type menu of the parquet node has no `DATE`. Opening such a node in the editor and pressing Done may reset the column to text (seen on 2026-10-17: an error `must be of type string or Buffer ... Received type number (20697)` and a text column filled with nulls). Do not edit a parquet node with a DATE column in the VFC: re-import the flow instead.
